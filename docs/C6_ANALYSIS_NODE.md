# ESP32-C6 — виносний вузол РАДІО-АНАЛІЗУ (план)

Модуль: **Waveshare ESP32-C6-WROOM-1** (RISC-V @160MHz, WiFi 6 2.4G, BLE 5, **802.15.4**,
native USB-Serial/JTAG).

## Навіщо (проблема, яку вирішує)
Головна ESP32 T-Display ОДНОЧАСНО тримає зв'язок (STA+AP+gateway/app) і робить аналіз.
Аналіз (sniffer/channel-monitor/deauth) вимагає promiscuous/channel-hop → рве WiFi-лінк →
«девайс відпадає» від сервера/додатка. Розділяємо ролі фізично:

```
        UI + ЗВ'ЯЗОК (ніколи не відпадає)            РАДІО-АНАЛІЗ (headless)
   ┌───────────────────────────────┐  wired link  ┌────────────────────────────┐
   │  ESP32 T-Display (HOST)        │◄────UART────►│  ESP32-C6 (ANALYSIS NODE)  │
   │  дисплей/кнопки, меню          │  921600 3.3V │  WiFi sniffer/mon/deauth    │
   │  WiFi STA+AP, gateway, app     │  (без дільн.)│  nRF24 2.4G, CC1101 sub-GHz │
   │  SD, EM, батарея, UNO-лінк     │              │  BLE, 802.15.4 (Zigbee/Thr) │
   └───────────────────────────────┘              └────────────────────────────┘
```
Хост лишається на мережі завжди; C6 крутить радіо як хоче. Результати: C6 → UART → HOST →
WiFi/gateway → сервер/додаток. Це і є «кабель-реле live-моніторингу» (backlog #15) у залізі.

## Що виграємо
- **Зв'язок не рветься під час аналізу** (головна ціль; закриває #4/#7 структурно).
- **Звільняються піни головної плати:** nRF24+CC1101 (спільний HSPI) їдуть на C6 →
  вивільняються G2/G15/G38 (SCK/MOSI/MISO), G25/G12 (nRF CSN/CE), G27/G39 (CC CS/GDO0) —
  ~7 GPIO. SD отримує ЧИСТУ виділену SPI (без MISO-перемикання), + запас під модульне
  розширення.
- **Нова здатність: 802.15.4** — сканер Zigbee/Thread/Matter (у ESP32/T-Display його нема).
- WiFi 6 (802.11ax) STA; для сніфінгу дає не так багато (monitor ловить кадри будь-як),
  але 15.4 — реальний плюс. Native USB → C6 можна ще й підключати прямо до сервера як
  окрему USB-плату (див. task 6/boardproxy) — паралельний аналіз, поки хост тримає UI.

## Компроміси
- C6 = 1 ядро RISC-V @160MHz (проти 2×240 у ESP32) — для ВИДІЛЕНОГО сніфера достатньо.
- Лише 2.4G (нема 5G) — як і в поточної системи.
- UART@921600 обмежує bulk-потік кадрів; для повного PCAP-стрімінгу — опційно SPI-slave
  (C6) з DMA пізніше. Для лічильників/подій/спектрів UART вистачає.

## Лінк-протокол (текстові рядки, дзеркало UNO-стилю; 3.3V↔3.3V — БЕЗ дільника)
HOST → C6 (команди):
```
SCAN WIFI                 повний скан AP
MON <ch|HOP>              channel monitor (канал або hop 1..13)
SNIFF <ch>                promiscuous, лічильники по MAC
DEAUTH                    лічити deauth/disassoc-кадри
RF24 SWEEP                зайнятість 126 каналів nRF24
SUBGHZ <freq_khz>         RSSI CC1101
BLE SCAN
Z15 SCAN                  802.15.4 енергоскан по каналах 11..26
STOP                      зупинити аналіз, звільнити радіо
STAT                      здоров'я вузла
```
C6 → HOST (результати/телеметрія, ~лінійно):
```
WIFI <ssid> <bssid> <rssi> <ch> <enc>
MONCH <ch> <count>
SNIF <mac> <rssi> <count>
DEA <count> <src_bssid>
R24 <ch> <count>
SGZ <freq_khz> <dbm>
BLE <addr> <rssi> <name>
Z15 <ch> <energy> <pan_hex>
STAT <free_heap> <temp_c_x10> <uptime_s>
EVT <type> <detail>
```

## Живлення C6 «за вимогою» (щоб не жерло без потреби)
C6 з радіо — найпрожерливіший вузол (сам nRF24 PA/LNA = ~115мА пік). Аналіз буває
рідко/сплесками, тож тримати C6 ввімкненим постійно — марна витрата. Два підходи:

**A. Жорстке гейтування живлення (РЕКОМЕНДОВАНО — істинний нуль у спокої).**
HOST через GPIO `C6_EN` керує high-side load-switch (напр. TPS22965 / AP22815 / MIC94xx) на
шині живлення C6. Аналіз потрібен → EN=1 → C6 (і його радіо) стартують; аналіз завершено/
idle-timeout → EN=0 → споживання ≈0 (лише витік ключа, одиниці µА).
- Плюс: у спокої НУЛЬ (гасяться і C6, і голодні радіо разом).
- Мінус: холодний старт ~0.5–1.5с (boot + init радіо), стан губиться.
- Handshake: HOST підіймає EN → чекає від C6 рядок `EVT boot c6-analysis` (вже є у скелеті)
  як «готовий» → шле команди. На STOP або після idle-timeout → EN=0.

**B. Deep-sleep C6 (тримаємо живлення, але спимо).**
C6 лишається під живленням, але у deep-sleep (~7–15µА). Будиться по GPIO wake-лінії від HOST
(або таймером для періодичних свіпів).
- Плюс: миттєве пробудження (десятки мс), можна тримати стан у RTC-памʼяті, простіша розводка
  (без ключа, лише wake-пін). Потрібен LDO з малим Iq.
- Мінус: не істинний нуль (µА + Iq регулятора).

**Правило вибору:** рідкісний аналіз (хвилини на годину) → A (load-switch, нуль). Частий/потрібна
миттєвість → B (deep-sleep + wake).

**ВАЖЛИВИЙ підводний камінь (обидва підходи, коли C6 знеструмлений):** не можна лишати HOST-TX
у «1», коли VCC C6 = 0 — струм потече в C6 через захисні діоди GPIO (back-powering / клямп).
Тому: (1) HOST переводить свої лінк-піни у Hi-Z/low ПЕРЕД зняттям EN; (2) на UART-лініях pull-
резистори, щоб HOST-RX не ловив сміття від плаваючого TX вимкненого C6. Опційно — series-резистор
або буфер на лінку.

**Інтеграція з power_guard:** не піднімати C6, якщо напруга батареї нижча за поріг (той самий
захист від брауну, що вже блокує радіо на HOST). Idle-timeout живе на HOST.

## Розподіл прошивки
- **HOST (T-Display):** аналіз-апки стають ТОНКИМИ проксі — шлють команду в C6, поллять
  результати, малюють. Радіо-драйвери nRF/CC із HOST переносяться на C6. Новий драйвер
  `src/drivers/c6_link.*` (дзеркало uno_link) — інтерфейс до вузла.
- **C6 (`firmware/esp32_c6/`):** headless-демон: читає команди, диспетчеризує в analysis/*,
  віддає рядки. Порт wifi_sniffer/channel_monitor/deauth_alert/rf24_analyzer/subghz/ble +
  новий z15_scan.

## Черга робіт (коли купиш)
1. Прошити C6 скелетом (`firmware/esp32_c6`), перевірити USB + STAT по UART.
2. Перенести nRF24+CC1101 на C6, перепінити HOST (звільнити HSPI, дати SD чисту шину).
3. Портувати аналіз-апки на C6; на HOST зробити remote-proxy обгортки.
4. 802.15.4-сканер (нова фіча).
5. Оновити iso-візуалізацію в додатку: 3 плати (T-Display + C6 + UNO).
